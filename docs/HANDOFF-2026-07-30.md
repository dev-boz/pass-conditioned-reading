## What happened

The maintainer read the measured per-pass cost back against the architecture and caught that the
implemented schedule is not the one the README specifies. Confirmed in code and archives:

- **README:** a tiling pyramid — pass 1 is the *whole document* compressed; level 2 is two halves,
  each compressed less; the last level is verbatim. Every level partitions the document. `k`
  indexes **resolution**.
- **What ran** (`planted.py::build_schedule`, D25 2026-06-13): 6 coarse chunks, then 25 verbatim
  tiles. **Two** resolution levels. Measured distinct compression ratios across all 31 passes:
  **`[1, 4, 5]`**. No pass ever sees the whole document.
- **It reaches the training data.** `teacher_gen.py:136` calls `build_schedule`, so the 277-doc
  corpus, the 5,730 rows and the LoRA were all built on the two-level schedule.

**This explains P1d.** The k/K channel measured inert because in training, position carried no
information beyond "which of two sweeps am I in" — and the stage rubric already said that.
**Falsifier F2's negative is withdrawn as a test of pass-conditioning.** The result that most
undermined the core idea was an artifact of the wrong schedule.

**Invalidated:** the Stage-A 0/10 verdict *as a verdict on Context Diffusion* (it stands as a
verdict on that instantiation); P1d/F2; the gauntlet's "k is not a sufficient statistic"
diffusion-kill (re-argue on the pyramid).

**Survives** (demand and within-pass findings — all would have bitten on the correct schedule):
relation never demanded (0/28), `ANSWER:` 0× in 5,730 rows, length gate dropped 52% of verbatim
rows, budget advisory-only, table→range binding loss (8/11 vs 1/11, p≈7.5×10⁻³), 94%-boilerplate
salience, 26% no-op REPLACEs + 10% clobber, compose scale ladder. Plus all infrastructure.

## ⚠️ The finding that needs the maintainer's decision

**G5 passes, but for a reason that changes the experiment.** No single pyramid view holds both
operands — because the extractive compressor **drops both operands at every compressed level**.
They appear only at the verbatim level (k=38 holds `23: 988`, k=56 holds the adder and the fn).

Under the old schedule the Phase-A views *did* carry both, because Phase A used the hand-built
`frozen_scaffold_v2`, not the compressor. The chain gate's `preflight` asserts this as **C1**
(*"the frozen scaffold carries the operands into Phase-A"*).

So on the pyramid, as built:
- **C1 no longer holds** and `preflight` will fail if pointed at the pyramid unmodified.
- There is **no early exposure** to the target facts at all — the "record coarse, refine fine"
  story has no early signal for these specific values.

That is arguably *more* faithful (compression is supposed to be lossy, and the question is whether
the model integrates anyway), but it is a different experiment and it is the maintainer's call.
Three options, in rough order of fidelity:
1. Accept it — operands surface only at verbatim; the architecture must carry them forward from
   there. Update C1 to assert the *verbatim* level carries them.
2. Use LLM-generated views for the compressed levels (as `frozen_scaffold_v2` was) so salient
   facts survive compression — closer to what DiSCo's compressor is meant to be, and the
   `gen_views_llm.py` path exists.
3. Re-plant the fixture so operands survive extractive compression.
